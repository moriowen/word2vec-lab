Deliverable 1

What the two architectures actually are

A word2vec model is two matrices and a dot product. There is no hidden layer and no nonlinearity. W_in holds one row per word and is the thing you keep. W_out exists only to compute the training loss and is discarded when training ends.

A and E, skip-gram with negative sampling. One centre word predicts each surrounding word independently. Instead of a softmax over all 14,309 words, each positive pair is scored against 10 negatives drawn from the unigram distribution raised to 0.75.

B, CBOW with hierarchical softmax. The context rows are averaged into a single vector that predicts the centre word. The output is a binary tree over the vocabulary, so one prediction costs log2(V) decisions rather than V.

On the handout's encoder / code / decoder framing. It is borrowed from autoencoders and fits word2vec only loosely. An autoencoder reconstructs its own input; word2vec reconstructs a neighbouring word, and it throws the decoder away. The mapping used above is the honest one: the one-hot input is the input layer, W_in is the encoder, the 300-dimensional row is the code, W_out is the decoder, and the context prediction is the output.

  1. Build the vocabulary from our corpus first intersect_word2vec_format only overwrites rows that already exist. It does not import Google's three million words, which is what we want, but it needs stating.
  2. Set vectors_lockf to ones explicitly gensim 4.x does not create it. Without it the import either fails or silently freezes every row, producing a model that looks fine-tuned and is not.
  3. Keep the learning rate low: alpha 0.005, 8 epochs Google never published their output matrix, so W_out starts random and the first updates are partly spent re-learning a decoder. A normal learning rate scrambles the imported vectors in the first epoch.
  4. Measure drift rather than assuming it Cosine between each word's warm-start vector and its final vector. Mean 0.9609, median 0.9731, so the low learning rate held.
Model E, beyond the requirement

Writing skip-gram with negative sampling

The handout suggests taking a superficial look at the code. Writing it instead is the difference between having used word2vec and understanding it. src/sgns.py implements the vocabulary and counts, subsampling of frequent words, the unigram^0.75 noise table, a dynamic window, the two embedding matrices, and linear learning rate decay. to_keyedvectors then wraps W_in in a gensim object so E runs through the existing evaluation code unchanged.

The first version did not learn, and the failure is worth keeping. Loss sat at exactly 1.3863 for all ten epochs and accuracy came out 0.4992, which is chance on a balanced split. 1.3863 is 2·ln 2, the loss of a model whose every logit is zero. The cause was the loss reduction, not the sampling: calling BCEWithLogitsLoss once on the positives and once on the negatives averages over B entries and over B·k entries, so at a batch of 8,192 the effective per-pair learning rate was about 3e-6. Measured gradient norm on W_in was exactly 0.0. Writing Mikolov's equation 4 directly, summing over the k negatives and averaging only over the batch, fixed it.

Two component checks were run before training anything, and they are what made that failure quick to localise. Subsampling keeps 17.6% of occurrences of the. The noise table maps the from a raw frequency of 4.30% down to a sampled 1.31% while lifting execrable from effectively zero to 2e-5. Both are the 0.75 exponent behaving correctly.

That is the argument for an approximate index stated as a measurement: at 14,309 words nobody needs one, at 500,000 it is 15 ms per query, and at Google's full three million it would be roughly 90 ms.

The 2 · V · d · 4 prediction holds within 3% for A, D and E. B comes in at 1.40 because hierarchical softmax also keeps the Huffman tree's code and point arrays, which the formula does not count.

C does not fit, and the cause is not established. 500,000 by 300 float32 is 600 MB and the measured delta is 195.6 MB, a third of it. The likely explanation is macOS memory compression, which compresses inactive anonymous pages so ru_maxrss reports below the allocation. That is testable: the same measurement on a Linux node should come out near 600 MB. Until it runs, this is an open discrepancy and not a finding.

One more measurement decided how E trains. On this vocabulary, MPS is slower than CPU (64.3 against 44.6 ms per batch) and sparse gradients are slower than dense (52.6 against 44.6). The GPU loses because the model is small enough that launch and transfer overhead dominate. Sparsity loses for a specific reason: a batch of 8,192 pairs with 10 negatives touches roughly 90,000 index slots over 14,309 rows, so nearly every row updates on every step and there is no sparsity left to exploit. Both results should reverse on a larger corpus, which is the measurement text8 exists to take.

Deliverable 6

Installation, running and measurement

Four things cost real time, and each reported something other than its actual cause. They are recorded here because the handout asks for the experience, and because each has a specific tell.

  1. gensim has no wheels for Python 3.14 The machine's default interpreter is 3.14. Installing gensim there tries to compile Cython from source and fails a long way in. Homebrew's Python 3.11 is what the virtual environment uses.
  2. import gensim fails on a fresh unpinned install gensim 4.3.x imports scipy.linalg.triu, which scipy 1.13 removed. The ImportError names gensim, so it reads as a broken gensim rather than a version conflict. requirements.txt pins scipy<1.13 and numpy<2.
  3. The SST-2 split with hidden labels The GLUE copy sets every test label to -1. Accuracy against it is meaningless and looks plausible. src/data.py asserts the test split is two-class and raises otherwise.
  4. Whole-process peak RSS is not a model measurement The first memory table compared process peak RSS against the matrix prediction and reported 297.8 MB for a model whose matrices are 34.3 MB. Peak RSS includes the interpreter, gensim, numpy, torch and the resident corpus. src/measure_mem.py now measures an RSS delta in an isolated subprocess per model.

Reproducing everything on this page is four commands after pip install -r requirements.txt: python -m src.main trains A and B and loads C, python -m src.run_eval adds the similarity, latency and error measurements, python -m src.measure_mem fills the memory table, and python -m src.build_report regenerates this page. Model E is python -m src.run_e and takes 160 seconds on CPU.
